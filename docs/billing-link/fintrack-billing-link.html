Decision Box

ปัญหาจริงไม่ใช่ลายเซ็น — คือ บิลกระดาษจดมือทำให้รายการ 20 บรรทัดหายไปเหลือบรรทัดเดียว แก้ด้วยการทำให้บิลเกิดในระบบตั้งแต่ตอนสั่งของในไลน์ แล้วทั้งสองอาการหายพร้อมกัน

เหตุผลหลัก
  1. สองอาการมีรากเดียวกัน — กระดาษจดมือคือสาเหตุที่พนักงานลงย่อเป็น “ของแห้ง” บรรทัดเดียว ไม่ใช่ปัญหาคนละเรื่อง
  2. ระบบเก็บ line_items อยู่แล้วแต่ไม่มีรายงานไหนอ่านมันเลย — ชิ้นที่ขาดคือ query กับหน้าจอ ไม่ใช่ตารางใหม่
  3. ตัวชี้เป็นตายคือแรงงานพิมพ์ — วางข้อความสั่งของจากแชทไลน์ (เห็นตัวอย่างจริงแล้ว แตกด้วย regex ได้) บวก เติมราคาล่าสุดอัตโนมัติ เหลือให้พนักงานแก้แค่ตัวที่เปลี่ยน
ขนาดงาน
SQL 1 บรรทัด · ไม่มีตารางใหม่เลย · endpoint ใหม่ 6 ตัว · parser 1 ไฟล์พร้อมเทสต์ · แก้ 3 ไฟล์หน้าจอ
คู่ค้าสองแบบ
บจก. มีใบส่งของพิมพ์อยู่แล้ว — ใบของเราจะซ้ำ จึงบันทึกรายการอย่างเดียว ไม่ต้องส่งลิงก์ให้เซ็น · รายเล็กที่จดมือถึงจะออกใบวางบิลเต็มรูป · ตัดสินด้วยคอลัมน์ doc_type ที่มีอยู่แล้วบน vendor_profiles
Confidence
สูง สำหรับการวินิจฉัย — ตามรอยในโค้ดจริงแล้วว่าข้อมูลตายตรงไหน · สูง สำหรับ parser ด้วย — เห็นข้อความสั่งจริงแล้ว รูปแบบคงที่พอที่ regex จะจับได้
จะพลิกถ้า
ร้านเปลี่ยนไปสั่งด้วยเสียงหรือส่งรูปแทนพิมพ์ → วางข้อความใช้ไม่ได้ ต้องถอยไปใช้ OCR ซึ่งรีโปมีอยู่แล้วในสายสลิป
ทำวันนี้ได้เลย
เขียน parseOrderText.mjs พร้อมเทสต์จากข้อความจริงในหัวข้อ 05 — ทำได้เลยโดยไม่ต้องรออะไร
01 — วินิจฉัย

ข้อมูลตายตรงไหน

ตามรอยจากบิลกระดาษถึงหน้ารายงาน ข้อมูลขาดสองจุด และจุดที่สองอยู่ในโค้ดปัจจุบัน

ต้นทาง คู่ค้าจดบิลใส่กระดาษ 20 รายการ — มีชื่อของ จำนวน ราคาต่อหน่วย ครบ
↓ พนักงานตรวจรับ
จุดที่ 1 · หายเพราะแรงงาน พิมพ์ 20 บรรทัดไม่ไหว → ลงเป็น “ของแห้ง ฿8,400” บรรทัดเดียว
↓ บันทึกลงระบบ
จุดที่ 2 · หายเพราะโค้ด ต่อให้กรอกรายการครบ line_items ก็ ไม่เคยข้ามไปตาราง transactions — ตอนกดจ่าย ระบบสร้าง transaction บรรทัดเดียวด้วยชื่อบิล
↓ รายงาน
ผลลัพธ์ รายงานทุกตัวสรุปจาก category_id / sub_category_id เท่านั้น — ละเอียดที่สุดที่เห็นได้คือ “ของแห้ง” ไม่มีทางเห็นมะนาวหรือกระเทียม

ข้อสรุปที่ต้องบอกตรง ๆ: ต่อให้สร้างฟีเจอร์ใบวางบิลจนเสร็จ Dashboard วัตถุดิบก็ยังทำไม่ได้อยู่ดี — เพราะ line_items ถูกอ่านแค่สองที่ในทั้งระบบ คือหน้าการ์ดบิลกับหน้าคู่ค้า และอ่านไปเพื่อแสดงผลเฉย ๆ ไม่มีการรวมยอดที่ไหนเลย

ทำแบบนี้ · คำนวณจากประวัติที่ซื้อจริง

ของแต่ละชิ้นถูกเก็บใน line_items ของบิลใบนั้น ๆ เท่านั้น · “ของที่คู่ค้ารายนี้เคยขายเรา” เป็นมุมมองที่คำนวณสดจากบิลเก่า ไม่ใช่ข้อมูลที่เก็บซ้ำ — แม่นกว่าเสมอ เพราะมาจากของที่ซื้อจริง

Autocomplete ควรจัดลำดับแบบนี้

พิมพ์ “มะ” ในบิลของ บจก. สดดี → ขึ้นของที่เคยซื้อจากสดดีก่อน แล้วต่อด้วยของที่เคยซื้อจากร้านอื่น · ของที่ไม่เคยซื้อจะไม่ขึ้น ครั้งแรกต้องพิมพ์เอง ซึ่งยอมรับได้ เพราะครั้งที่สองเป็นต้นไปมันจำให้แล้ว

อย่าเอาไปปนกับ keywords ที่มีอยู่แล้ว

vendor_profiles.keywords จาก Merchants 3.0 มีไว้ค้นหาร้าน (“ร้านไหนขายถุงมือ”) เป็นข้อความอิสระที่คนกรอกเอง — คนละแกนกับรายการของในบิล ปล่อยไว้อย่างเดิม อย่าเอามารวมกัน

จะต้องมีตารางสินค้าจริง ๆ เมื่อไหร่

ตอนที่จะอ่าน PDF ราคารายวันใน P2 — เพราะ PDF มีของที่ร้านขายทั้งหมด ไม่ใช่แค่ที่เราเคยซื้อ ตอนนั้นถึงจะมีเหตุผลให้เก็บแยก · ก่อนหน้านั้นการเก็บซ้ำมีแต่จะทำให้ข้อมูลสองชุดไม่ตรงกัน

Rollback: ซ่อนปุ่ม “ออกใบวางบิล” และแท็บวัตถุดิบ แล้วปล่อยคอลัมน์ vendor_ack ว่างไว้ — โหมดรับของเดิมและ LINE bot ไม่ถูกแตะ ยกเว้นเงื่อนไข evidence_key ที่ไม่มีวันเป็นจริงกับบิลเดิม

09 — กฎที่ห้ามยืดหยุ่น

6 ข้อที่ทำให้ข้อมูลและหลักฐานยังใช้ได้จริง

  1. ตัวแตกข้อความห้ามบันทึกเงียบ ๆ ต้องโยนตารางให้คนตรวจและกดยืนยันทุกครั้ง — ข้อมูลผิดที่ไหลเข้าเงียบ ๆ แพงกว่าไม่มีข้อมูล
  2. Dashboard ต้องแสดงเปอร์เซ็นต์ความครอบคลุมคู่กันเสมอ ห้ามโชว์กราฟลอย ๆ ที่ทำให้เข้าใจว่าเห็นครบทั้งร้าน
  3. คู่ค้ายืนยันแล้ว = ล็อกรายการ แก้ยอดไม่ได้อีก ถ้าต้องแก้ให้ยกเลิกใบแล้วออกใหม่ — ไม่งั้นลายเซ็นผูกกับตัวเลขที่เปลี่ยนไปแล้ว
  4. ยืนยันได้ครั้งเดียว ทับซ้ำไม่ได้ ลบไม่ได้ · ใบที่จ่ายแล้วห้ามยืนยันย้อนหลัง
  5. เอกสารห้ามเรียกว่าใบเสร็จรับเงิน เราเป็นผู้จ่าย ไม่ใช่ผู้รับเงิน — ใบวางบิล / ใบตรวจรับ / ใบสำคัญจ่ายเท่านั้น
  6. ลิงก์สาธารณะต้องมี rate limit ตั้ง Cloudflare rate limiting ที่ /receipt/* ก่อนเปิดใช้จริง ไม่งั้นยิงเดา token ได้เรื่อย ๆ
10 — ความเสี่ยง

จุดที่พังง่ายที่สุด และวิธีกัน

ความเสี่ยงโอกาสความแรงวิธีกัน
พนักงานเลิกกรอกรายการ กลับไปลง “ของแห้ง” บรรทัดเดียว — งานทั้งหมดเสียเปล่า สูง สูง วางข้อความจากแชทต้องอยู่ใน MVP ไม่ใช่ P2 · วัดทุกสัปดาห์ว่ากี่ % ของยอดซื้อมีรายการละเอียด ถ้าตัวเลขตก แปลว่าการกรอกยังหนักเกินไป
ชื่อของเพี้ยนสะสม — หกเดือนผ่านไปมีชื่อซ้ำเป็นร้อย Dashboard อ่านไม่ออก สูง กลาง autocomplete ทำให้ทางที่ถูกเป็นทางที่ง่ายที่สุด · เพิ่มเครื่องมือรวมชื่อซ้ำใน P1 ก่อนที่จะสาย ห้ามรอถึงปีหน้า
ข้อความสั่งของไม่ได้เป็นรายการ — สั่งด้วยเสียง ส่งรูป หรือโทรบอก กลาง สูง ยังไม่รู้จนกว่าจะเห็นข้อความจริง — เช็คก่อนเขียนโค้ด · ถ้าเป็นรูป ทางออกคือ OCR ซึ่งรีโปนี้มีอยู่แล้วในสาย slip
ราคาไม่มีในข้อความสั่ง พนักงานไม่เติม ยอดเป็นศูนย์ สูง กลาง เตือนก่อนออกใบถ้ามีบรรทัดราคา 0 แต่ไม่บล็อก (ของแถมมีจริง) · ยอดรวมแสดงตัวใหญ่ให้เห็นชัดว่าผิดปกติ
ของที่ส่งจริงไม่ตรงกับที่สั่ง — สั่งมะละกอ 30 กก. ชั่งได้ 28.5 กก. สูง กลาง ข้อความที่วางเป็นแค่ตัวตั้งต้น · พนักงานต้องแก้เป็นจำนวนที่ชั่งได้จริงตอนรับของ ก่อนออกใบ — Dashboard นับของที่รับจริง ไม่ใช่ที่สั่ง
ลิงก์ไปโผล่ในกลุ่ม 10 คน — คนของเราเองก็กดยืนยันแทนคู่ค้าได้ กลาง กลาง เขียนบนหน้าให้ชัดว่า “สำหรับผู้ขายเท่านั้น” · บันทึกชื่อคนกดและแสดงบนใบทั้งสองฝั่ง ใครกดแทนกันจะเห็นทันที · เป็นเหตุผลเสริมว่าทำไมลายเซ็นถึงไม่ควรเป็นเงื่อนไขปล่อยเงิน
คู่ค้าไม่กดยืนยันสักที กลาง ต่ำ เตือนแต่จ่ายได้ เงินจึงไม่ค้าง · ลิงก์วางในแชทที่สั่งของกันอยู่แล้ว ไม่ใช่ช่องทางใหม่ · ไม่กดเกิน 3 ใบ ให้ถอยกลับไปเซ็นต่อหน้ากับรายนั้น
พนักงานแก้ยอดหลังคู่ค้าเซ็น แล้วโอนตามยอดใหม่ ต่ำ สูง กฎข้อ 3 — ล็อกรายการหลังยืนยัน บังคับในโค้ด ไม่ใช่ในระเบียบ
ลิงก์ถูกส่งต่อ คนนอกเห็นรายการ ยอด และสลิป กลาง กลาง token 64 ตัวเดาไม่ได้ + rate limit · เลขบัญชีปิดเหลือ 4 ตัวท้าย · ถ้ากังวลสลิป ให้แสดงข้อมูลการโอนแทนรูปเต็ม

2 ของแห้งชุดเดิมถูกสั่งซ้ำจากคู่ค้าเดิมบ่อย ๆ autocomplete ช่วยน้อยลง และ “สั่งซ้ำจากใบก่อน” ใน P2 ไม่คุ้มทำ ดูบิลย้อนหลัง 1 เดือน ว่ารายการซ้ำกันกี่ %
3 json_each() ใช้ได้บน Cloudflare D1 ต้องสร้างตาราง bill_items จริงและเขียนตอนออกใบ — งานเพิ่มราวครึ่งวัน ไม่ถึงกับพลิกแผน ยิง query เดียวบน D1 จริง ใช้เวลา 5 นาที ทำก่อนเริ่มเขียน
4 ราคาต่อหน่วยถูกตกลงตอนรับของ ไม่ใช่หลังจากนั้น ต้องให้แก้ราคาได้หลังออกใบ ซึ่งชนกับกฎล็อกใบ ต้องออกแบบทางยกเลิก/ออกใหม่ตั้งแต่ MVP ถามพนักงานที่รับของว่ารู้ราคาตอนไหน
6 doc_type บน vendor_profiles ถูกกรอกไว้ครบพอที่จะใช้แยกคู่ค้าสองแบบ ต้องไล่กรอกก่อน ไม่งั้นระบบจะสั่งส่งลิงก์ให้ บจก. ที่มีใบส่งของอยู่แล้ว เปิดหน้าร้านค้า ดูว่ากี่รายที่ยังว่าง ใช้เวลา 5 นาที
5 ข้อโต้แย้งเรื่องยอดกับคู่ค้าเกิดจริงพอที่จะคุ้มทำปุ่มยืนยัน ตัดปุ่มยืนยันทิ้ง เหลือแค่ส่งลิงก์ให้ดู — แต่ส่วนเก็บข้อมูลรายการยังคุ้มอยู่ดี เพราะคนละเป้าหมาย นับย้อนหลัง 3 เดือน มีกี่ครั้งที่ยอดไม่ตรงกับที่ตกลง
